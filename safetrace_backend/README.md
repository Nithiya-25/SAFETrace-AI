SAFETrace AI — Backend (Member 2)
1. Purpose
This backend is the bridge between Member 1's AI/computer-vision module (person detection + tracking) and Member 3's investigator dashboard. It:
Stores missing-person case, video, track, detection, evidence, and lead data.
Receives AI results and turns them into explainable lead scores.
Exposes everything through a REST API (FastAPI) so the dashboard never touches the database directly.
SAFETrace is an investigation-support tool. It never confirms a missing person's identity. All AI-derived output is framed as a "Potential Lead" that requires investigator verification. The prototype is built and tested only against authorized/sample video — it does not claim access to police databases or real government CCTV systems.
2. Technology stack
Python 3
FastAPI + Uvicorn
Pydantic (request/response validation)
SQLite (via the standard-library sqlite3 module — no ORM)
Pandas available for any offline data-processing needs
pytest for tests
No Postgres, Redis, Docker, Kafka, microservices, or auth servers in Round 1.
3. Database schema
cases (case_id PK, name, age, gender, last_seen_location, last_seen_time,
       description, reference_image, status, created_at)

videos (video_id PK, case_id FK -> cases, camera_id, location, filename,
        uploaded_at, status)

tracks (id PK autoincrement, track_id, video_id FK -> videos,
        first_seen, last_seen, duration, frame_count, average_confidence,
        UNIQUE(video_id, track_id))
        -- Member 1's track_id is only unique within a video, so the
        -- real key is (video_id, track_id).

detections (detection_id PK, track_id, video_id FK -> videos,
            frame_number, timestamp, x1, y1, x2, y2, confidence)

evidence (evidence_id PK, case_id FK, video_id FK, track_id, camera_id,
          location, timestamp, evidence_image, detection_confidence,
          lead_score, status, created_at)

leads (lead_id PK, case_id FK, evidence_id FK -> evidence, score,
       priority, reason, status, created_at)
Relationship:
cases -> videos -> tracks -> detections
cases -> evidence -> leads

7. How Member 1 sends AI results
POST /ai-results with a JSON body shaped like sample_ai_result.json at the project root:
{
    "video_id": "VID-001",
    "tracks": [
        {
            "track_id": 7,
            "first_seen": "00:00:10",
            "last_seen": "00:00:27",
            "duration": 17,
            "frame_count": 510,
            "average_confidence": 0.89,
            "visual_similarity": 0.86,
            "time_location_score": 0.9,
            "crop_paths": ["outputs/person_crops/track_7/frame_120.jpg"],
            "detections": []
        }
    ]
}
Notes:
visual_similarity is optional. If Member 1's appearance/re-ID model isn't ready yet, omit the field (or send null) — the backend will not fake a value. It's clearly labeled "not yet available" in the lead's reason text and simply contributes 0 to that 30% of the score until a real value is supplied.
time_location_score is optional and defaults to a neutral 0.5.
crop_paths are referenced, not copied — the evidence record just stores the path to Member 1's chosen representative crop.
The backend does not import or call any of Member 1's Python code directly; the only contract is this JSON shape over the API.
8. How Member 3 consumes the API
The dashboard should never open data/safetrace.db directly — it talks to FastAPI only:
Streamlit -> GET /cases/MP-0001/leads -> FastAPI -> SQLite -> JSON -> Streamlit
Typical dashboard flow:
GET /cases                         (list cases)
GET /cases/{case_id}               (case detail)
GET /cases/{case_id}/evidence      (evidence table)
GET /cases/{case_id}/leads         (priority queue, sorted)
PATCH /evidence/{evidence_id}/status   (investigator review actions)
9. Lead scoring formula
Explainable, weighted, documented — never a black box.
Lead Score = 0.40 x Detection Score
           + 0.20 x Duration Score
           + 0.30 x Visual Similarity Score
           + 0.10 x Time/Location Score
Detection Score — the track's average detection confidence (0–1).
Duration Score — track duration in seconds, scaled 0–1 and saturating at 30 seconds (a 30s+ continuous track scores the max 1.0).
Visual Similarity Score — from Member 1's future re-identification model. If not supplied, treated as 0 for scoring purposes and flagged as unavailable in the explanation — never invented.
Time/Location Score — relevance of the video's time/location to the case's last-seen details (0–1). Defaults to 0.5 (neutral) if not supplied.
Result is scaled to 0–100 and mapped to priority:
80–100  -> HIGH
60–79   -> MEDIUM
0–59    -> LOW
Worked example (Section 31 of the spec):
Detection = 0.90, Duration = 0.80 (24s / 30s cap), Visual Similarity = 0.85, Time/Location = 0.90

0.40(0.90) + 0.20(0.80) + 0.30(0.85) + 0.10(0.90)
= 0.36 + 0.16 + 0.255 + 0.09
= 0.865  ->  86.5  ->  HIGH
Every lead also gets a plain-language reason string, e.g.:
High detection confidence (90.0%); Long continuous track (24s);
Strong visual similarity (85.0%); High time/location relevance

"Verified" means a human investigator reviewed the evidence — it does not mean the AI independently confirmed identity.
11. Error handling
Unknown case/video/evidence IDs return 404 with a clear message (e.g. "Case MP-9999 does not exist").
Invalid status values on the PATCH endpoint are rejected with 422 (Pydantic enforces the three allowed values: Pending Review, Verified, Rejected).
Lead/evidence scores are always clamped to the 0–100 range.
12. Tests
pytest tests/
Covers case creation, video creation, AI-result ingestion, scoring math (including the documented worked example), evidence generation, lead sorting, and status verification — both at the service layer and through the live HTTP API (tests/test_api.py, using FastAPI's TestClient).
13. Privacy / security notes
Built and demoed only with sample/authorized video.
Does not expose real personal information beyond what an investigator explicitly enters for a case.
Does not claim integration with police databases or real government CCTV systems.
All AI output is a "Potential Lead" pending human review — never a confirmed identity.
